# Gift Bot

Telegram-бот для создания, публикации и полного жизненного цикла розыгрышей. Epic 3 добавляет автоматическое завершение, неизменяемый снимок участников и билетов, немедленную публикацию победителей и приватный перевыбор одного места.

## Локальный запуск

Нужны Node `24.18.1` (допустимый диапазон `>=24.18.0 <25`) и pnpm `11.15.1` (диапазон `>=11.15.1 <12`). Проверить контракт:

```sh
node --version
pnpm --version
```

Установить зависимости, создать локальную конфигурацию и применить миграции:

```sh
pnpm install
cp .env.example .env
pnpm db:migrate
```

Заполните только локальный `.env`:

```dotenv
BOT_TOKEN=<token from BotFather>
TEAM_TELEGRAM_IDS=<comma-separated numeric Telegram user IDs>
DATABASE_PATH=.data/gift-bot.sqlite
LOG_LEVEL=info
DRAW_MEMBERSHIP_CONCURRENCY=10
```

`TEAM_TELEGRAM_IDS` — allowlist операторов. Не добавляйте токен, ID команды или SQLite-файлы в Git.
`DRAW_MEMBERSHIP_CONCURRENCY` ограничивает параллельные финальные проверки Telegram; значение по умолчанию — `10`.

Команды проекта:

```sh
pnpm dev          # TypeScript long polling
pnpm build
pnpm start        # запуск собранного dist/index.js
pnpm check        # lint + tests + build
pnpm db:generate  # сгенерировать новую миграцию после изменения схемы
pnpm db:migrate   # применить существующие миграции
```

`pnpm dev` и `pnpm start` используют long polling, поэтому не запускайте два экземпляра с одним ботом одновременно. Перед polling процесс восстанавливает незавершённые публикации и фоновые задачи; при остановке он дожидается и Telegram updates, и выполняющегося фонового прохода перед закрытием SQLite.

## SQLite и резервная копия

По умолчанию база находится в `.data/gift-bot.sqlite`. Включён WAL: нельзя надёжно копировать только основной файл пока процесс пишет в базу — часть последних данных может находиться в `-wal`. Остановите бота и копируйте согласованную пару базы и её `-wal`/`-shm` файлов, либо используйте штатный SQLite backup. Перед восстановлением сделайте отдельную копию текущей базы. При `SIGINT`/`SIGTERM` процесс сначала останавливает long polling, перестаёт принимать новые updates, дожидается уже начатых обработчиков и только затем закрывает SQLite.

## Операторский сценарий

В [BotFather](https://t.me/BotFather) создайте тестового или рабочего бота и сохраните выданный token только в `.env`. В каждом публичном канале добавьте бота администратором с правами **публиковать**, **редактировать** и **удалять** сообщения. Канал обязан иметь `@username`.

Свой канал:

1. Оператор из `TEAM_TELEGRAM_IDS` запускает `/new` и проходит шаги: внутреннее название 1–100 символов, 1–50 победителей, будущий дедлайн по Екатеринбургу, рефералы, текст или фото с подписью.
2. На шаге каналов выбирает «Добавить свой канал», открывает `startchannel`-ссылку и добавляет бота администратором с тремя правами.
3. После события Telegram бот показывает найденный канал; оператор нажимает подтверждение, открывает предпросмотр и публикует. И событие, и callback подтверждения требуют, чтобы оператор всё ещё находился в `TEAM_TELEGRAM_IDS`.

Внешний канал:

1. Оператор на шаге каналов выбирает «Пригласить владельца» и передаёт владельцу одноразовую `/start ci_…`-ссылку (24 часа). Экран подключения показывает точный момент истечения в ISO UTC.
2. Владелец открывает ссылку, добавляет бота через предложенную `startchannel`-ссылку и нажимает подтверждение найденного канала.
3. Это связывает канал только с данным розыгрышем. Владелец не получает доступ к `/new`, `/giveaways` или `/cancel`.

Предпросмотр отправляет будущий конкурсный text или photo/caption отдельным сообщением точно в финальном формате; список каналов, предупреждение и кнопка запуска идут следующим сообщением и не расходуют лимит конкурсного поста. Исходные пробелы и Telegram entities сохраняются, поэтому их offsets не сдвигаются; ввод только из пробельных символов отклоняется.

Перед публикацией бот заново получает текущие `@username`, title, админский статус и все три права каждого канала. Метаданные сохраняются только после успешной проверки всех каналов; пропавший публичный username или право блокирует запуск без publication run, join-token, delivery и отправок. Один и тот же контент публикуется во все подтверждённые каналы; розыгрыш становится `active` только когда сохранён `messageId` каждой доставки. Итоговое опубликованное text-сообщение ограничено 4096 UTF-16 code units, caption фото — 1024; лимит включает название и служебные строки. Переполнение итогового render отклоняется до создания publication run, join-token или delivery.

Каждый опубликованный пост сразу содержит строку `Зарегистрировано участников: 0`. При вводе контента бот резервирует место для значения вплоть до `Number.MAX_SAFE_INTEGER`, поэтому последующее обновление счётчика не переполняет Telegram text/caption.

## Участники и рефералы

Кнопка «Участвовать» открывает личный чат через непрозрачную `join_…`-ссылку. Для новой регистрации бот последовательно проверяет каждый канал: собственный admin-статус и membership пользователя. Допустимы `creator`, `administrator`, `member` и `restricted` только при `is_member=true`; ошибки, неизвестный статус, `left`, `kicked` и потеря bot-admin прав работают fail closed.

- Если подписка неполная, бот показывает отдельную публичную ссылку на каждый отсутствующий канал и actor-bound кнопку повторной проверки.
- При Telegram `429` автоматического повтора интерактивного запроса нет: ответ показывает рекомендованное ожидание и новую кнопку.
- Успешная регистрация уникальна по `giveaway + Telegram user ID`. Повторный `/start` или callback обновляет доступные username/display name, но не меняет первую дату регистрации и inviter.
- При включённых рефералах каждый успешный просмотр статуса выпускает новую непрозрачную `ref_…`-ссылку. Старые ссылки действуют до закрытия розыгрыша; raw join/referral/callback tokens не сохраняются.
- Учитываются только прямые сохранённые связи. Текущий информационный расчёт — `1 + floor(directReferrals / 3)`; на дедлайне Epic 3 повторно проверяет eligibility и включает в snapshot только связи между допустимыми участниками.

Первая регистрация транзакционно помечает счётчик каждого опубликованного поста dirty. Обновления coalesced, выполняются не чаще раза в минуту, сохраняют исходные text/caption entities и кнопку участия. Ошибка одного edit не откатывает регистрацию: только этот пост остаётся на retry. Отмена имеет приоритет над pending counter work, отзывает join/referral links, убирает кнопку и остаётся финальной правкой.

## Итоги и перевыбор

Не реже раза в минуту процесс атомарно захватывает `active`-розыгрыши с наступившим дедлайном. Тот же проход выполняется при старте, поэтому выключенный в момент дедлайна Mac подхватывает розыгрыш после следующего запуска. Перед snapshot бот заново проверяет публичность и права каждого канала, затем membership всех зарегистрированных участников. `429` соблюдает `retry_after`, network/5xx ограничены тремя попытками; любой оставшийся неизвестный ответ переводит розыгрыш в `failed` без выбора.

Успешная проверка один раз сохраняет versioned snapshot, допустимые прямые referrals, число билетов и полный порядок, перемешанный через `node:crypto`. Snapshot защищён SQLite-trigger от изменения. Выбор заполняет уникальными пользователями все доступные места, остальные фиксирует как пустые и сразу переводит розыгрыш в `completed` — ручного review-gate нет. Исходные посты заменяются актуальным нумерованным результатом без внутренних причин и истории, а winner/team уведомления доставляются через durable outbox.

В карточке завершённого розыгрыша `/giveaways` оператор может выбрать занятое место, ввести приватную причину длиной 3–500 символов и подтвердить перевыбор. Бот продолжает исходный ticket order: действующие и ранее отклонённые победители пропускаются, однозначно отписавшиеся кандидаты получают внутреннюю причину `subscription_missing`, а неизвестный membership оставляет текущего победителя и cursor без изменений. Транзакция меняет только выбранное место; повтор callback возвращает сохранённую операцию. «История перевыборов» доступна только allowlisted команде и показывает оператора, причину, старое/новое место, пропуски и состояние доставки.

## Ошибки, восстановление и отмена

- После запуска сначала обрабатываются незавершённые публикации. Даже если у всех delivery сохранены `messageId`, автоматическая активация после crash запрещена: состояние становится `failed` с `activation_uncertain/telegram_posts_unverified`, без проверочного Telegram-вызова и повторной отправки. Частично известные доставки удаляются в обратном порядке; полный откат возвращает `draft`.
- Неизвестный результат отправки, `sending` при падении процесса, сомнение в активации или неудачный откат переводят в `failed`. Бот не повторяет такую отправку автоматически. Выполните `/giveaways`: карточка `failed` показывает ID розыгрыша, stage, error kind, а для затронутых каналов — `@username`, внутренний channel ID, Telegram chat ID и ссылку на известный пост. Сверьте эти данные с реальными постами и структурированным событием `publication_failed`, затем отмените согласованный failed-розыгрыш; не публикуйте поверх неизвестного состояния.
- После перехода в `active`, терминального `failed` или `cancelled` мастер закрывается, поэтому следующий `/new` создаёт свежий черновик. Failed-розыгрыш при этом остаётся доступен в `/giveaways` для диагностики и отмены.
- `/giveaways` показывает отдельную карточку и actor-bound кнопку «Отменить» для каждого принадлежащего оператору `draft`, `active` или `failed`. В карточке также видны participant count, режим рефералов, состояние синхронизации, ожидающие или недоставленные draw-уведомления и active предупреждения о правах каналов. Персонального списка участников нет. `/cancel` при нескольких целях сначала просит выбрать точную цель, а затем всегда требует подтверждения.
- При отмене сообщение заменяется на «Розыгрыш отменён», а кнопка участия убирается. Текст может быть укорочен, чтобы suffix поместился в лимит Telegram.
- Если проверка обнаружила, что бот больше не администратор канала, новые регистрации блокируются, в SQLite остаётся одно active предупреждение, а создателю отправляется durable-уведомление. Следующая успешная проверка закрывает предупреждение.

## Безопасность и границы Epic 3

Join/referral ссылки не содержат внутренних ID. Retry callback хранит только server-side inviter candidate и привязан к Telegram actor; bearer-token в payload не переносится. Replay уже использованного participant callback разрешён и возвращает текущее состояние без дубликата.

Храните `BOT_TOKEN` и ссылки-приглашения как секреты. Токены в базе хешируются; callback payload переключения содержит только invite ID, а actor binding, активное состояние и expiry повторно проверяются по сохранённым данным — исходный invite token в callback не попадает. Не логируйте и не пересылайте токены широким группам. Не делайте внешнего владельца участником allowlist только для подключения канала. Событие `publication_failed` содержит `giveawayId`, `stage`, `errorKind`, `channelId` и `channelUsername`, но никогда token, `BOT_TOKEN` или deep-link payload.

Не добавлены автоматическое распознавание ботов, CAPTCHA, приватные каналы, экспорт, web/API, второй уровень рефералов или LaunchAgent. Подозрительность победителя остаётся человеческим post-publication решением и никогда не задерживает исходный результат.
