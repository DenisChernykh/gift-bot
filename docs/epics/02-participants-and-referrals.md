# Epic 2 — Участники и опциональные рефералы

**Требования PRD:** `PARTICIPANT-01`, `PARTICIPANT-02`, `PARTICIPANT-03`, `REFERRAL-01`, `REFERRAL-02`

**Зависимость:** [Epic 1 — создание и публикация](./01-giveaway-creation.md)

**Следующий эпик:** [Epic 3 — итоги и перевыбор](./03-draw-and-reroll.md)

## 1. Цель

Дать пользователю понятный и идемпотентный вход в активный розыгрыш, допуская только подписанных на все каналы участников и при необходимости начисляя дополнительные билеты за действительных прямых рефералов.

## 2. Пользовательский результат

- Участник переходит из конкурсного поста в личный чат и сразу понимает, выполнены ли условия.
- После подписки он повторяет проверку без новой ссылки и регистрируется один раз.
- При включённых рефералах он получает персональную ссылку и видит прогресс до следующего билета.
- Команда видит число зарегистрированных участников, не выполняя экспорт персональных данных.

## 3. Сценарии ролей

### 3.1. Участник без реферала

1. Нажимает «Участвовать» в канале.
2. Открывает `/start join_<join-token>`.
3. Если подписка неполная, получает ссылки на недостающие каналы.
4. Нажимает «Проверить ещё раз».
5. После успешной проверки получает подтверждение участия.

### 3.2. Приглашённый участник

1. Открывает `/start ref_<referral-token>`.
2. Проходит ту же проверку подписки.
3. При первой успешной регистрации связывается с пригласившим.
4. Последующие ссылки не меняют уже сохранённого пригласившего.

### 3.3. Пригласивший участник

После регистрации получает персональную ссылку, число действительных прямых рефералов на текущий момент и пояснение: каждые 3 допустимых реферала на дедлайн дают один дополнительный билет.

### 3.4. Член команды

В карточке розыгрыша видит уникальное число зарегистрированных участников, состояние обновления постов и включённость реферальной программы. Персональный список и экспорт в этом эпике отсутствуют.

### 3.5. Внешний владелец

Не получает доступ к числу участников в административном интерфейсе и не может запрашивать сведения об отдельных пользователях.

## 4. Функциональные требования

### 4.1. Deep links

- Для каждого активного розыгрыша существует непрозрачный join token.
- Реферальная ссылка содержит отдельный непрозрачный token, однозначно связанный с розыгрышем и пригласившим.
- Payload соответствует ограничениям Telegram и не содержит raw database ID, Telegram ID пригласившего или секретов.
- Join token активен только в состоянии `active`; referral token дополнительно требует включённых рефералов и действительного пригласившего.
- Неверный, отозванный или относящийся к завершённому розыгрышу token не создаёт участника.
- В SQLite сохраняется только SHA-256 hash join/referral token. Каждый успешный status-view при включённых рефералах выпускает новую ссылку; все ранее выпущенные ссылки остаются действительны до закрытия giveaway.
- Кнопка повторной проверки использует отдельный actor-bound callback token. Server-side payload содержит `giveawayId` и опциональный inviter candidate, но не исходный bearer-token; replay уже использованного participant callback разрешён как идемпотентный status-view.

### 4.2. Проверка подписки

- Проверка выполняется через Telegram для каждого канала текущего розыгрыша.
- Каналы проверяются последовательно. Перед membership пользователя бот должен по-прежнему иметь статус администратора канала.
- Допустимы статусы `creator`, `administrator`, `member`; эквивалентный активный membership допускается только когда Telegram явно сообщает `is_member=true`.
- `left`, `kicked` и неизвестный результат считаются невыполненным условием.
- При неполной подписке пользователь получает уникальный список недостающих каналов и кнопку повторной проверки.
- Ошибка одного канала не заменяется предположением: регистрация ждёт успешной проверки всех каналов.
- Интерактивные Telegram-вызовы автоматически не повторяются. Для `429` ответ показывает `retry_after`, для остальных ошибок — новую actor-bound кнопку без обещания успешной проверки.
- Потеря ботом административных прав блокирует новые регистрации и создаёт уведомление команде.

### 4.3. Регистрация

- Запись участника создаётся только в `active` и только после полной проверки.
- Непосредственно перед insert одна SQLite-транзакция повторно проверяет `state=active`, `now < deadlineUtc`, включённость рефералов и inviter из того же giveaway с более ранним `joinedAt`.
- Уникальный ключ — `giveawayId + telegramUserId`.
- Сохраняются Telegram ID, доступные username/display name, время первой регистрации и опциональный inviter ID.
- Telegram ID является идентичностью; изменение username не создаёт нового участника.
- Повторный вход возвращает существующий статус и не изменяет `joinedAt` или inviter.
- Успешное повторное взаимодействие обновляет только доступные username/display name.
- Участник без username имеет те же права и шансы.
- После перехода в `drawing`, `completed`, `cancelled` или `failed` новые регистрации запрещены.

### 4.4. Реферальная программа

- При выключенной программе join flow не создаёт inviter relation и не показывает реферальные кнопки.
- При включённой программе персональная ссылка появляется только после регистрации пригласившего.
- Пригласивший должен существовать в том же розыгрыше и иметь более ранний `joinedAt`.
- Self-referral отклоняется.
- Один приглашённый связан не более чем с одним пригласившим.
- Повторный `/start` по чужой ссылке не переносит участника.
- Один приглашённый даёт не более одного зачёта и только прямому пригласившему.
- Текущий прогресс информационный: окончательный зачёт определяется Epic 3 после повторной проверки на дедлайн.
- Число билетов на дедлайн: `1 + floor(validDirectReferrals / 3)`.

### 4.5. Счётчик участников

- Счётчик равен числу уникальных зарегистрированных участников независимо от числа билетов.
- Первая регистрация каждого нового уникального участника в той же транзакции coalesce-ит по одной `participant_count` задаче на опубликованный пост.
- Обновление всех dirty-постов выполняется пакетно; один пост редактируется не чаще одного раза в 60 секунд.
- Повторные взаимодействия уже зарегистрированного пользователя не помечают счётчик повторно.
- Ошибка редактирования одного поста сохраняет задачу retry и не отменяет участие.
- `429` переносит `availableAt` минимум на Telegram `retry_after`; остальные ошибки счётчика получают минутный retry.
- Counter edit сохраняет исходные text/caption entities и существующую кнопку участия.
- Текст явно говорит «Зарегистрировано участников», чтобы не обещать финальную eligibility до дедлайна.
- Канонический renderer публикует значение `0` сразу, а валидация контента резервирует длину для `Number.MAX_SAFE_INTEGER`.

### 4.6. Отмена, восстановление и предупреждения

- `cancel_message` и `participant_count` обрабатывает один сериализованный durable synchronizer без overlapping worker.
- Отмена транзакционно отзывает join/referral tokens и supersede-ит pending/processing counter work. Cancellation edit идёт последним и удаляет кнопку участия.
- При частичном edit только неуспешный пост остаётся pending; участие и referral relation не откатываются.
- Перед long polling runtime возвращает зависшие `processing` задачи в `pending`. При shutdown он ждёт текущий background pass перед закрытием SQLite.
- Потеря bot-admin прав создаёт не более одного active alert на `giveaway + channel + kind`. Unnotified alert переживает restart и отправляется создателю; успешная следующая проверка переводит его в `resolved`.
- `/giveaways` остаётся creator-only и показывает participant count, режим рефералов, sync-state и active rights warnings без персонального списка.

## 5. Состояния и переходы

### 5.1. Попытка участия

| Состояние розыгрыша | Результат |
|---|---|
| `active` + подписка полная | Создать или вернуть участника |
| `active` + подписка неполная | Показать каналы и повторную проверку |
| `active` + Telegram error | Fail closed и предложить повторить позже |
| Любое другое | Сообщить, что участие закрыто |

### 5.2. Реферальная связь

`absent -> assigned` только при первой успешной регистрации. Перехода `assigned -> another inviter` нет.

### 5.3. Синхронизация счётчика

`clean -> dirty -> syncing -> clean`, а при ошибке `syncing -> dirty` с отложенным повтором.

## 6. Ошибки и граничные случаи

- Одновременные запросы одного пользователя дают одну запись благодаря уникальному ограничению и транзакции.
- Referral token может выпустить только уже зарегистрированный inviter. Неизвестный, cross-giveaway, self или потерявший валидность inviter candidate не создаёт новую запись; связь задним числом не создаётся.
- Ссылка из другого розыгрыша не смешивает участников и рефералов.
- Если рефералы выключены после создания черновика, ранее показанные preview-ссылки недействительны; после публикации настройка неизменяема.
- Удаление одного конкурсного поста не меняет число участников и не закрывает остальные ссылки.
- Пользователь, отписавшийся после регистрации, остаётся в счётчике зарегистрированных, но может быть исключён финальной проверкой.
- Блокировка личного чата после регистрации не удаляет участие.
- Ошибка пакетного счётчика не вызывает повторной регистрации и не меняет referral relation.

## 7. Критерии приёмки

- Подписанный пользователь регистрируется из каждого опубликованного канала как один участник.
- Неподписанный пользователь видит все отсутствующие каналы и регистрируется после повторной успешной проверки.
- Telegram error и потеря прав бота не создают ложного участника.
- Повторные `/start`, callback и Telegram update не создают дубликат.
- Пользователь без username успешно участвует.
- При выключенных рефералах ссылки и начисления отсутствуют.
- При включённых рефералах self-referral, смена inviter и двойной зачёт невозможны.
- Для 0, 2, 3 и 6 действительных прямых рефералов формула даёт соответственно 1, 1, 2 и 3 итоговых билета.
- Счётчик отражает уникальных участников, обновляется не чаще раза в минуту и восстанавливает синхронизацию после ошибки.
- Отмена имеет приоритет над dirty counter work и остаётся финальной правкой после возможной гонки.
- Потеря и восстановление bot-admin прав соответственно создают дедуплицированный warning и закрывают его.

## 8. Проверка

- Unit: разбор deep-link payload, eligibility mapping, idempotency decisions, referral invariants и формула билетов.
- Integration: уникальные ограничения SQLite, конкурентная регистрация, неизменяемый inviter и очередь обновления счётчика.
- Telegram adapter: все membership statuses, `429/retry_after`, network/5xx, actor-bound callback replay и потеря прав.
- Migration: чистая база, повторное применение, upgrade со схемы `0005`, `integrity_check` и `foreign_key_check`.
- Ручной Telegram smoke: участие из двух каналов, дозапись после подписки, пользователь без username и цепочка из трёх прямых рефералов.

## 9. Не входит в эпик

- финальная eligibility и фиксация снимка;
- случайный выбор и перевыбор;
- капча и эвристики аккаунта;
- рефералы второго уровня;
- изменение правила `3 = +1`;
- экспорт, рассылка и публичный список участников;
- приватные каналы и `launchd`.
